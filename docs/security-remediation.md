# Targeted security remediation

## Assessment

The tracking RPC requires the exact order reference and a matching email or primary phone. It returns a limited projection and uses the same null response for an unknown reference or incorrect contact. Predictable legacy references still let someone who knows a contact try multiple references. Client-IP limits alone do not bind attempts across different clients.

New orders use the existing reference field with a random UUID-derived value containing 122 random bits. Confirmation, email, tracking, and admin continue to use the existing field. Existing references, checkout response contracts, and saved idempotency results stay intact. For references outside the new format, checkout enforces 12 attempts per contact per UTC hour across references and client IPs. The existing 60/hour per-client cap still applies. Email case and supported phone formatting are normalized for counters. The stored counter keys contain HMACs of contacts. The RPC still controls access and preserves historical exact-match behavior.

An attacker who knows a historical contact may still consume that contact's budget or make limited attempts. Alternate historically accepted phone spellings outside the normalizer can use separate counters. A contact cap also affects legitimate users sharing a contact. Review aggregate 429 rates before adjusting limits. Stronger verification for historical orders would require a verified delivery or account flow and is deferred.

The migration revokes direct client access to the order and product sequences. Checkout and product-code reservation use their function owners. Client sequence reset was reproduced only in isolation. No public endpoint for sequence manipulation was established.

Public policies now hide inactive editions and their sizes. Existing operations policies let MFA-verified owners and admins manage inactive inventory. Existing product and collection teaser metadata remains public by design. This change protects variant rows and stock data. The public image bucket has separate visibility rules.

## Receipt reconciliation

Read-only production metadata showed 11 private payment receipt objects. Four are registered under the current workflow. Two are linked to orders with matching stored receipt paths, and two are unclaimed.

Seven objects were created before the current registry workflow, with two in July, two in August, and three in September 2026. None has the current gateway path shape. None matched a registry entry or an order receipt path after direct matching, path-suffix matching, query stripping, and decoding encoded slashes. Creation dates and paths are consistent with older workflows. They do not establish who uploaded each object or whether it supports a completed, pending, or disputed payment.

Among these seven objects, zero are confirmed linked, zero are confirmed safe to delete, and seven remain uncertain. The bucket is private. The current cleanup only selects registered unclaimed objects after its grace period. No files were opened, moved, deleted, or added to that cleanup. Reconcile them with authorized finance and dispute records, document retention requirements, and obtain separate deletion authorization for any objects proven eligible.

## Validation and release

- App and Edge TypeScript checks, ESLint, production build, and 61 automated tests passed.
- Isolated PostgreSQL exercised historical and random reference tracking, fee and stock integrity, receipt linkage, promo rollback, idempotency, sequence privileges, product-code reservation, and public/admin catalog visibility.
- Mocked gateway tests verify that different references and IPs share the legacy contact limit, a denied request never reaches the tracking RPC, and random references continue using the existing per-client cap. Previous audit tests remain in place.
- Localhost port 5173 targets production Supabase. No write tests used that instance.
- The compatibility run used a reference generated by the migrated PostgreSQL allocator through the real checkout handler with mocked Turnstile. The browser consumed that fixture through mocked HTTP endpoints. Microsoft Edge at 390 and 1440 px verified the full reference in confirmation, tracking, admin search and packing slips, including print media. The notification handler sent both templates to a mock provider. Edge rendered the captured HTML at both widths without horizontal overflow and verified the customer tracking link.
- This does not exercise third-party mail clients, physical printers, or hosted traffic and database contention. Contact counters use the existing indexed per-key hourly rows. A legacy lookup adds one counter RPC and serializes concurrent updates only for the same key. The existing expiry sweep still runs with each counter increment, so latency under concurrent load remains unmeasured.

For an authorized release:

1. Deploy the checkout Edge Function with its existing shared module, JWT, secrets and origin settings. It is compatible with the existing database and starts protecting historical tracking immediately.
2. Deploy the frontend and the send-order-notification Edge Function. Both must be ready before new references are generated. Preserve the notification function's current JWT, recipient and provider settings.
3. Confirm the allocator precondition and exact policy names immediately before applying the migration. The read-only production check matched both, confirmed the reference column is text, and confirmed that the checkout RPC is unavailable to anon and executable by service_role. The migration is transactional and generates longer references only for new orders.
4. Verify the frontend, deployed functions, sequence and policy metadata, and authorized historical tracking. Verify new references through naturally placed orders or an isolated environment. Do not create a production order solely for verification.

The inventory audit semantics and other lower-priority findings remain in the original audit. No production grants, configuration, receipts, orders, or stock were modified.
